## 🎯 주요 해결 과제

### 1. CS 기반 현장 프로그램의 웹 전환 제안 및 구현

**배경:** 사내에서 현장 프로그램을 VB.NET 기반 클라이언트로 개발해왔으나, 담당 개발자들이 퇴사하면서 기존 현장 프로그램 유지보수조차 어려운 상황. 신성산업 프로젝트에서 현장 프로그램 개발 방향이 화두가 됨

**제안:**

- 당장 개발보다 이후 유지보수가 더 큰 문제임을 파악
- 현장 프로그램을 웹으로 개발하자고 직접 제안
- 키오스크 환경 특성상 앱으로 감싸야 하는 부분은 신규 담당자와 협업하여 구현

**구현:**

- 현장 프로그램 내 모든 기능 및 로직 직접 구현
- 하이브리드 앱 기반 키오스크 환경에 맞춘 웹 구조 설계 및 개발

**결과:**

- 사내 웹 개발자들이 유지보수 가능한 첫 웹 기반 현장 프로그램 확립
- 이후 다른 프로젝트에서도 해당 구조를 틀로 채택하여 사내 표준으로 자리잡음

---

### 2. 프레임워크 4.0 버전업 — 프로시저 중심 로직의 서비스 계층 이관

**배경:** 신성산업 프로젝트를 기점으로 사내 웹 프레임워크를 3.0에서 4.0으로 버전업하는 작업을 병행. 가장 큰 변화는 DB 프로시저 중심 로직을 MyBatis 서비스 계층으로 이관하는 것

**구현:**

- 기존 프로시저 앞뒤 트랜잭션 방식에서, 서비스 레이어에서 트랜잭션 범위와 롤백 기준을 명시적으로 정의하는 구조로 전환
- MyBatis 매퍼 파일을 테이블 단위로 분리하고, 복잡한 프로시저 로직 대신 간단한 조인 쿼리 수준으로 단순화하여 재사용성과 유지보수성 향상
- ANSI 표준 SQL 사용으로 향후 MSSQL 외 다른 DB로 전환 시에도 코드 변경 없이 대응 가능하도록 설계
- 서비스 계층을 화면 서비스와 테이블 서비스로 분리 — 비즈니스 로직은 화면 서비스에, 테이블 관련 CRUD는 테이블 서비스에서 담당하도록 구조화하여 코드 중복 제거 및 범용성 확보

**결과:** 데이터 정합성 확보 및 코드 구조 명확화

---

### 3. 설계 충돌로 인한 반복 재작업 문제 해결

**배경:** 신규 PM이 사내 프레임워크와 로직에 익숙하지 않아, 주어진 설계대로 개발하면 다른 로직에서 말이 안 되는 상황이 반복 발생. 개발 → 오류 발견 → 설계 뒤집기 → 재개발 사이클이 반복되며 일정 지연

**해결:**

- PM·실무 개발자·이사까지 전원이 참여하는 전체 회의를 직접 제안
- 플로우 맵을 함께 그리며 설계 로직을 단단히 정립
- 모듈 단위로 완료될 때마다 관련자들과 긴밀히 협의하며 로직 확정

**결과:** 반복 재작업 사이클 제거, 기한 내 납기 완료

---

### 4. 기존 DB 설계 한계로 인한 로직 불일치 해결

**문제:** 기존 DB 구조는 설비 하나에 작업지시 하나만 처리하는 구조였으나, 신성산업은 배치 작업 방식으로 하나의 설비에 여러 작업지시를 동시에 처리해야 했음. 이로 인해 설비 가동률 계산 시 중복 집계가 발생하여 데이터 정합성이 무너지는 문제 발생

**해결:**

- 브릿지 테이블을 설계하여 설비와 작업지시 간의 관계를 별도로 관리
- 설비 작업 시작 시: 해당 설비에 진행 중인 작업지시가 있는지 확인 후 브릿지 테이블에 등록
- 설비 비가동·작업 완료 시: 스캔한 작업지시가 해당 설비의 마지막 작업지시인지 확인 후 실제 비가동 데이터 입력 여부를 결정

**결과:** 배치 작업 환경에서도 설비 가동률 데이터 정합성 확보

## 💡 회고

- 유지보수 한계를 먼저 파악하고 웹 전환을 직접 제안한 경험을 통해, 눈앞의 개발 문제뿐 아니라 운영과 유지보수를 고려한 구조적 사고의 중요성을 체감했습니다.
- 프로시저 중심에서 서비스 계층 중심으로 트랜잭션 구조를 직접 전환하면서, 트랜잭션 경계를 명확히 하는 것이 유지보수에 얼마나 중요한지 실감했습니다.
- 처음으로 후배를 리드하며 메인 개발자 역할을 맡아, 개발과 팀 관리를 병행하는 경험을 했습니다.
- 설계가 주어져도 로직 충돌이 반복될 수 있다는 것을 경험하며, 전체 흐름을 먼저 확정하고 개발에 들어가는 것이 얼마나 중요한지 배웠습니다.
